# Windows 执行权限兼容与回退边界

　　1.1.2 的托管启动和更新入口在启用目标核心前检查执行权限能力。已经保存权限策略或审批记录时，缺少相应能力的旧核心被拒绝启动，原始策略、任务和项目文件保持不变。当前保护覆盖新版托管入口，不能替代使用旧安装器覆盖新版启动器后的降级验收。

## 1. 能力契约

　　核心的 `version --json` 增加 `execution_policy_version: 1`。检查读取目标二进制的实际输出，不按产品版本号推测支持情况。旧 1.1.1 的版本输出没有此字段，因此能力值为零。

　　`internal/executioncompat` 只检查用户数据目录下的 `execution/permissions/policy.json` 或审批记录是否存在。存在记录时要求权限能力版本 1，即使记录损坏也不会允许旧执行器忽略。未知路径、符号链接、非目录和读取错误保持失败，不改写原文件。没有相应记录时保留原有旧版本恢复行为。

　　能力探测只执行目标核心的只读版本命令，截止时间为 5 秒，输出限制为 64 KiB，Windows 下不创建可见控制台。探测失败或能力不足均不启动目标执行器。

## 2. 执行入口

| 入口 | 检查时机与结果 |
| --- | --- |
| 稳定 Core 启动器 | 启动服务端或执行操作前检查目标核心。版本查询、状态、停止及限定恢复入口仍可用。 |
| 稳定 Tray 启动器 | 启动旧界面前检查，防止旧界面自动启动无权限引擎的核心。 |
| 新版服务管理 | `service start/restart` 的启动阶段检查实际活动核心。 |
| Generation 更新 | 暂存或停止原核心前检查目标能力，失败时保留当前版本。 |
| 新版 Arbiter 回退 | 恢复旧文件和指针后，重新启动核心、界面或隧道前检查。能力不足时保留停止状态并返回错误，不标记健康恢复。 |

　　能力不足返回 `EXECUTION_POLICY_DOWNGRADE_BLOCKED`。用户需要保留当前核心或恢复支持权限引擎的版本。兼容检查本身不修改操作系统权限、网络配置、认证材料或工作区文件。

　　本地归档更新还有既有的版本限制：目标必须比当前版本更新。测试将此拒绝与新增能力拒绝分别识别，不删除原来的降级限制。

## 3. 原生回归

　　`test-windows-execution-compatibility.ps1` 在独立目录和随机本机端口启动新版核心，经认证 API 创建任务并保存只读策略。随后将测试实例指针切到真实 1.1.1 核心，验证稳定服务端入口、服务启动和界面入口均拒绝旧执行器。恢复新核心后实际请求文件写入，必须返回权限拒绝且目标文件不存在。任务、策略和项目文件逐字节保留。

　　测试使用从 1.1.1 归档提取的核心。在 CI 中使用固定提交 `7505e8044c6daa78ed73c603a2dd9ff214883d82` 构建同一旧实现，不通过修改新核心的版本字符串伪造旧执行器。所有进程、文件和监听端口均属于该测试目录，生产配置不参与测试。

　　Inno 生命周期测试分开处理两个阶段：首次升级前保持未使用新权限的 1.1.1 状态；成功升级后再引入新策略，并验证同版本失败回退、修复、卸载和重装保持该策略。直接在旧版本阶段注入新策略并要求旧核心照常执行，不属于安全回退的通过条件。

## 4. 剩余验收

　　运行旧安装器可能同时替换新版稳定启动器，直接启动旧 generation 也不经过新版检查。这两条路径尚未形成自动安全降级闭环。正式发布的 `rollback_preserves_data_and_permission_intent` 继续为 false，直到产品支持的完整降级路径有实际隔离和恢复证据。

　　Windows ARM64 验证通过独立托管运行器执行，并在运行前检查操作系统和 Go 工具链架构。WPF 回归显式使用 `win-arm64`，不能将 x64 仿真进程计为原生界面验收。CI 配置已接入，完成状态以具体运行结果为准。

　　上述保护与宿主对话元数据无关，不增加业务工具的 ConversationID 输入。真实 ChatGPT 元数据和重连验收仍须使用实际宿主请求，模拟客户端的 `_meta` 不能代替。
