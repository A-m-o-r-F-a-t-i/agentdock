# AgentDock Workbench 1.1.8

　　1.1.8 继续完成 1.1.7 原修改计划中尚缺的原生恢复、Windows 元数据保真、键盘交互及性能验收。新版本继承已合并的三层权限、插入回执与独立消息行、输出字符设置和 Workbench 名称。已发布的 1.1.7 标签与资产保持原样，新运行时修改使用独立版本，不把新验收结果记到旧安装包上。

## 1. Windows 恢复事务

　　安装备份增加 Windows owner、group、DACL 和支持的文件属性记录。备份、暂存和恢复后均核对原生元数据，覆盖受保护 DACL、继承 DACL、旧继承标记以及只读、隐藏和归档属性。安全描述符恢复使用 Windows 备份流语义，避免通常的权限设置 API 把原始继承状态重新计算后当作原样恢复。

　　备份不静默丢弃无法保存的元数据。发现附加数据流（ADS）、扩展属性（EA）、reparse point，以及不支持的压缩、稀疏、加密等对象时，在 journal 提交和目标替换前拒绝本次备份，保留源对象。目录深度、数量、总内容字节和元数据大小都有预算。POSIX 普通文件的权限保留和链接拒绝规则继续使用原有测试。

　　计划任务的 `task.xml` 和 `state.json` 分别原子发布，XML 摘要与原任务权限保留。恢复前先验证存在状态、XML 和描述符，再停止或删除对应任务。缺少这些记录的历史备份不再被当作已验证恢复，返回保留位置和人工核对要求。原生进程退出状态未知时，不启动并发回滚，不删除有恢复价值的材料。

　　任务调度器可能将旧的纯 Allow DACL 规范化：显式条目前移，并增加自动继承标记。本版只接受每个 ACE 二进制内容、重复数和各组相对顺序不变的这种转换，分别报告“完全相同”或“纯 Allow 规范化”。SID、权限位、保护状态或继承标记变化，以及 Deny、对象或回调 ACE 重排，都使验证失败并保留备份。这个限定比较器不用于普通文件。恢复任务定义时禁用 registration trigger 的自动触发，避免恢复本身额外运行任务动作。

## 2. 原生故障与交互验证

　　新增强制 Windows x64/ARM64 原生验收，使用独立 GitHub runner、随机任务名和临时目录。测试调用实际 Task Scheduler COM、NTFS 和进程等待接口，覆盖双向权限转换中的准备、应用、验证、取消、恢复失败、恢复后验证失败、原生进程未知、任务定义篡改，以及原任务不存在。额外验证显式拒绝规则的精确恢复和额外授权条目被拒绝。测试不操作用户的生产 Core 或计划任务。

　　原子文件写入增加创建、权限设置、部分写、短写、同步、关闭、替换及替换后失败等九个故障边界。每次失败均检查完整的旧或新 journal、仍可读取的备份引用和临时文件清理。恢复测试增加真实文件占用、恢复中断后继续、准备内容属性被修改时停止等场景。

　　项目更多按钮补齐真实 WPF 窗口上的 Enter/Space KeyEvent 验证，经过 Button 类处理器进入同一分页操作，不直接调用 Click 方法冒充键盘测试。空页和已删除历史项也加入回归：空组锚点不可见、不可继续点击，旧请求不能覆盖新搜索或折叠状态。明暗主题、800/1280 窗宽和四档渲染 DPI、100 轮分页循环继续验证。这些是隔离自动化输入和渲染测试，不声称测试了所有物理键盘与显示器。

## 3. 注册表和上下文性能

　　注册表暖读保留有界的不可变序列化快照，并在跨进程锁内逐字节核对真实文件。相同版本复用解析结果和索引，变化、取消、所有权、终止、删除和外部写入仍按原规则处理，不能仅凭 mtime 或文件大小复用旧权限。

　　与每次重新计算全文哈希相比，未变化文件减少了 CPU 成本和临时分配。代价是每个注册表实例多保留一份最多 16 MiB 的编码快照。相同机器、Go 1.26.5、相同记录形状的三轮交替测量用于核对原计划的 10,000 条暖读十倍目标，不能把另一台机器或旧工具链的数字混入对比。

　　完整 `Runtime.Call(agentdock_context)` 另有无插件、实际规模模拟和 160 Skill 三类测试，共 960 个冷、暖和并发请求，保留每个 call_id、阶段耗时、构建次数、注册表读取/解析量和失败状态。该测量包含完整根调用和编码，未包含 ChatGPT 页面或外部网络传输。最终源码 SHA 对应的数据与逐项验收表随交付证据保留。

## 4. 全平台真实安装发布门禁

| 目标 | 构建与安装验证范围 | 主要安装资产 |
| --- | --- | --- |
| Windows x64 | 原生恢复与 WPF 回归、Core/桌面构建、隔离安装/修复/卸载 | `AgentDockSetup-amd64.exe`、`agentdock_windows_amd64.zip` |
| Windows ARM64 | ARM64 runner 原生恢复、安装包实际运行、隔离安装/修复/卸载 | `AgentDockSetup-arm64.exe`、`agentdock_windows_arm64.zip` |
| Linux x64 | 原生 Core、DEB 实际安装/验证/移除、RPM 独立根事务 | `agentdock-workbench_1.1.8_amd64.deb`、`agentdock-workbench-1.1.8-1.x86_64.rpm` |
| Linux ARM64 | 对应架构原生 Core、DEB 实际安装/验证/移除、RPM 独立根事务 | `agentdock-workbench_1.1.8_arm64.deb`、`agentdock-workbench-1.1.8-1.aarch64.rpm` |
| macOS Intel | 原生后端与 App 合同、x64 运行载荷 | `agentdock_darwin_amd64.tar.gz` |
| macOS Apple Silicon | 原生后端与 App 合同、ARM64 运行载荷 | `agentdock_darwin_arm64.tar.gz` |
| macOS 通用桌面 App | 双架构签名完整性、内嵌 Core 版本和摘要 | `AgentDock-macos-universal.dmg`、`AgentDock-macos-universal.zip` |

　　Linux 同时提供分架构 tar.gz。DEB/RPM 提供 Core 与核心 Skill，不启动服务，也不包含 Windows WPF 活动中心。RPM 使用对应 CPU 上的真实包事务引擎和独立根目录，不等同于全面完成 Fedora/RHEL 各版本兼容测试。macOS 保持现有原生 App。

　　1.1.8 起，发布器必须取得 Windows 两架构原生恢复、x64 安装、ARM64 原生安装、Linux 两架构包事务和 macOS 双目标验证的同 SHA 证据。缺项、失败、不同源码、大小或摘要不符均停止发布，不能用编译成功替代安装成功。完整资产上传草稿后再次核对，最后转为正式 Latest。所有资产继续附 SHA-256、`SHA256SUMS` 和 `release-manifest.json`。

## 5. 兼容与范围

　　安装路径、命令名、服务标识、Bundle ID 和升级资产命名不变。`agentdock version` 与 JSON 产品字段使用 AgentDock Workbench，旧 `--version` 首行继续兼容 1.1.6 更新器。原三层权限依然是工具准入限制，不是操作系统进程沙箱；自动审查依赖管理员单独配置可信审查程序。

　　插入消息继续区分内层附加、外层转发、接收端回执和宿主上下文确认。外部 ChatGPT `functions.exec` 仍需宿主接入受信任转发接口；没有这项证据时不显示已经进入模型上下文。直接调用与有界补充重投不会重复执行原工具。

　　Windows 新备份包含原生元数据版本。恢复进行中或原生状态未知时不得降级、删除恢复目录或混用旧恢复器。缺少原生保真/任务权限记录的旧材料需要使用其对应版本核对，不能自动补造字段。1.1.7 的插入和权限 schema 2 继续沿用。

　　Windows 发布者 Authenticode 签名与 macOS Developer ID 公证仍未配置；macOS App 使用 ad-hoc 签名。原计划明确将签名单列，本版不以自动验收冒充已签名。完整 R01–R09、F01–F11 映射见 `docs/acceptance-1.1.8.md`，实际运行号、失败历史、最终源码与测试计数以本版交付报告和发行清单为准。
