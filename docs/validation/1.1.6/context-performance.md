# AgentDock 1.1.6：P0 分阶段性能与正确性记录

本记录对应独立上游整合提交 `fc2f93832867352de6f6a6d81119ddb85e524b1a` 之后的 P0 源码修改，不代表 1.1.6 的协议、UI、GitHub 构建或正式发布已经完成。

## 测量边界

- 执行环境：Windows / Go 1.26.5，同机隔离生成夹具；没有修改或重启生产 AgentDock，没有连接用户真实 MCP 服务。
- 计时从正常的 `Runtime.Call(agentdock_context, workdir)` 开始，到返回对象 JSON 编码完成；包括根调用观测、规则、工作区、任务索引和能力摘要，不使用精简的 `AgentDockLocalContext` 冒充正常入口。
- 冷态：每次重建独立 Runtime，清除构造阶段建立的插件快照，规则/Skill/公共 Skill 缓存为空。Runtime 构造时间另存 `runtime_startup_ms`。未清操作系统文件缓存，也不把该数据称为完整 Windows 进程启动时间。
- 三组分别为无插件；5 个插件/51 Skill/5 MCP/3 Heavy 的匿名冻结配置；20 个插件/160 Skill/20 MCP/10 Heavy。实际规模来自 2026-09-23 原生插件目录读取，正文、命令和地址全部为生成的测试数据。
- 每组 100 次热调用、20 次冷调用、10 组各 10 次并发冷调用和并发热调用，共 960 次。P95 使用 nearest-rank；失败样本不被静默移出分母。

## 定位与修复，不补造旧版本成绩

早先仅测试内部 LocalContext 的 160 Skill 首次 38 ms / 热 5–6 ms 不能代表完整根调用。改用完整入口的首轮预检实际暴露大规模热 P50 205.985 ms、并发热 P95 2019.608 ms。分项显示 MCP 元数据路径在每次摘要读取时仍逐成员创建和加固插件数据目录，且处在共享注册目录锁下。

已把目录创建/权限准备移至选定服务真正连接或刷新前；摘要路径只读取不可变目录。实际连接前仍核对成员启用、拥有者、文件系统解析后边界和目标一致性，取消及路径替换均拒绝派发。上表是随后完整采样，不把预检当成旧版本基线。

未优化的 160 Skill 隔离基线曾达到 6 分钟测试上限且没有完整分位数，因此不存在可用的“优化前 P95”，不能计算或宣传精确加速倍数。六条历史慢调用保留各自身份及已记录总耗时，不补造 RPC/执行/等待分项。

## 实现与专项证据

共享构建有容量、总截止时间及并发边界；独立等待者取消不影响其余等待者，最后等待者退出取消构建。规则、插件、托管 Skill、公共 Skill 分层缓存；文件监测覆盖同长度同时间戳改写，Windows 稳定父目录监测不阻碍插件目录替换。正常与构造失败路径均释放监测和缓存。

MCP 元数据刷新、注册目录文件锁、服务器调用锁均传入调用方截止时间，不生成取消后仍可能取得锁的孤儿 goroutine。读取摘要不等待未选中的正在执行服务。Heavy 未定向展开不读取其完整 Skill 正文或启动成员。显式重读返回完整内容，而不是“已经发过”。

## 尚不能由本报告证明

本报告不覆盖 ChatGPT 网络/模板渲染延迟，不覆盖尚待实现的批量完整 Schema 端到端链，不证明实际模型减少了 context 次数，也不声称已经安装或实机验收。完整协议与 UI 验收结果由后续独立提交和发布验收记录给出。
