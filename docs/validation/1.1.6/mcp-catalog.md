# AgentDock 1.1.6：MCP 完整目录与批量 Schema 验证

## 实现

已知服务可直接使用 mcp_tool_list 返回完整目录，每项仅名称和一行描述。mcp_tool_inspect 的 names 支持 server:tool、server:* 以及跨服务混合选择，去重并稳定排序；旧 name 在同一入口归一化，无第二套执行器。完整输入/输出 Schema、$defs/$ref、嵌套限制与标准元数据保留。服务禁用、未知工具或单服务失败逐项报告，不抹掉成功项。

后台使用同一份完整分页工具目录供摘要、inspect 和执行校验共享。SDK tools/list_changed 通知、配置更改和一分钟受控过期使对应目录失效。十个并发冷读只构建一份完整目录；有效热目录不等待同服务正在执行的业务工具。返回的 Schema 深复制，不允许调用方修改验证缓存。读取或缓存不绕过插件成员启用和原权限规则。

每次业务响应均附完整目录，来自缓存而非重新请求 tools/list。装配顺序为原业务多内容块、目录摘要、可信用户插入，结构化业务对象/目录/guidance 分别保留。业务错误与传输失败仍保持原错误，不因目录可读而伪装成功，不重试副作用。目录不可用仅标明目录不完整。

## 验证

200 工具、每页 75 项的真实 SDK HTTP 夹具完成三页发现；10 并发只请求这三页。热目录在业务锁被占用时仍立即可读。真实 SDK 通知和过期刷新各只追加三页，失效前不重复发现。返回 Schema 被修改不会污染后续查询或 $ref 参数校验。

跨服务查询得到 203 个完整 Schema；重复选择去重、排序稳定。混合有效工具/未知服务/禁用服务/未知工具，成功结果保留，三个错误各自明确。成功、业务错误、传输错误与图片/文本/插入同时存在的响应顺序测试通过。

`go test ./... -p 2 -count=1 -timeout=8m` 全部通过。未启用真实桌面界面、未替换生产 AgentDock。

## 完整发现链性能

正常 Runtime.Call 与各步 JSON 编码的 context → 完整目录 → 完整 200 Schema → 第一次业务调用。21 次独立 Runtime 冷路径，100 次热路径，共 121 次，零失败。每次冷路径 tools/list 三页，所有热路径新增分页请求数 0。构造及配置准备不在本测量内，OS 文件缓存未清，不宣称包含 ChatGPT 网络和渲染。P95 为 nearest-rank。

| 模式 | 样本 | 总路径 P50 ms | 总路径 P95 ms | 最大 ms | 目录 P95 ms | 200 Schema P95 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| cold | 21 | 319.875 | 408.131 | 435.605 | 119.773 | 103.560 |
| hot | 100 | 304.124 | 441.401 | 1392.983 | 96.781 | 99.498 |

所有原始数值样本在 mcp-discovery-end-to-end.json。最大热路径为 1.393 s，未隐藏慢样本；P95 达到对应缓存目标。该报告不证明真实模型减少了工具发现次数。

## 边界

没有给目录套用搜索的 10/100 条上限，也没有静默截断 Schema。已测 200 工具和跨服务完整载荷；外部宿主对任意大响应的实际硬上限和续取路径尚未完成验收，不能据此声称已覆盖所有宿主容量。其余活动输出、即时投影、编辑统计和 UI 按独立阶段继续实施。
